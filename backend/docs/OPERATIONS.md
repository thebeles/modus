# Эксплуатация

`docker compose -f backend/deploy/docker-compose.yml ps -a` показывает состояние процессов. Контейнер migrate после успеха завершается с кодом 0. Проверка /api/v1/health/live проверяет процесс, /api/v1/health/ready проверяет соединение с PostgreSQL. Если API недоступен, начните с `docker compose -f backend/deploy/docker-compose.yml logs migrate api worker`.

Worker опрашивает очередь каждые две секунды. Уведомления создаются с уникальным ключом. Повторная обработка безопасна. Ошибки доставки повторяются с экспоненциальной задержкой. После шести попыток задача отображается в «Мониторинге». Перезапуск продолжает обработку открытых заданий. Настройте мониторинг числа ожидающих и исчерпанных заданий для промышленной эксплуатации.

Compose хранит PostgreSQL и вложения в именованных томах. Если текущий стенд был запущен с собственным именем проекта, передайте то же имя через `-p`, чтобы подключить существующие тома.

## Производственный запуск

В [production Compose](../deploy/docker-compose.production.yml) используются внешний PostgreSQL, мигратор и приложение с разными строками подключения, закрытый порт API и отдельный том файлов. Мигратор владеет схемой и выполняет `migrate deploy`. Подготовьте отдельную runtime-роль без владения таблицами, расширенных полномочий или членства в роли мигратора. Разрешите мигратору создать `pg_trgm` либо установите расширение через DBA. После первой и каждой последующей миграции выполните от владельца схемы `psql "$MIGRATION_DATABASE_URL" -v runtime_role=modus_runtime -f backend/deploy/runtime-grants.sql` с именем фактической runtime-роли. Для `psql` используйте строку подключения без параметра Prisma `schema`. Журнал аудита допускает чтение и добавление, а UPDATE, DELETE и TRUNCATE запрещены триггером и привилегиями.

Команды ниже выполняются из корня репозитория. Скопируйте [пример переменных](../deploy/.env.production.example) в `backend/deploy/.env.production`. Задайте `DATABASE_URL`, `MIGRATION_DATABASE_URL` и `WEB_ORIGIN=https://...` в этом файле или через окружение. Укажите `WEB_PORT`, если 5173 занят. Настройте внешний HTTPS reverse proxy на локальный порт веб-сервиса и сохраните браузерный Origin. Запустите `docker compose --env-file backend/deploy/.env.production -f backend/deploy/docker-compose.production.yml up -d --build`. Подайте `BOOTSTRAP_ADMIN_EMAIL` и `BOOTSTRAP_ADMIN_PASSWORD` через менеджер секретов в одноразовую команду `docker compose --env-file backend/deploy/.env.production -f backend/deploy/docker-compose.production.yml run --rm -e BOOTSTRAP_ADMIN_EMAIL -e BOOTSTRAP_ADMIN_PASSWORD api node dist/prisma/bootstrap-admin.js`. Добавьте обычную резервную очередь и резервные очереди специальных классов с действующими координаторами.

В «Мониторинге» администратор видит отметку последнего успешного цикла, размер очереди и число исчерпанных заданий. Сигнал считается устаревшим через 90 секунд. Повтор доставки возвращает задание в очередь с прежним ключом и записью аудита. Worker заново проверяет получателя и объект перед созданием уведомления.

## Резервная копия

Согласуйте окно записи, сохраните согласованные снимки базы и тома файлов. Для PostgreSQL используйте `pg_dump -Fc -f modus.dump` с настроенными `PGHOST`, `PGDATABASE`, `PGUSER` и безопасным источником пароля. Копии храните в зашифрованном хранилище с отдельным доступом. Для проверки восстановите дамп командой `pg_restore --exit-on-error -d <отдельная-база> modus.dump`, подключите копию тома и проверьте карточку, вложение и обработку outbox. Используйте отдельные секреты и закрытый тестовый адрес для восстановления.

## Редакционный процесс и файлы

Измерения и верификация могут ссылаться на подтверждающие файлы. Выдача проверяет текущий доступ к улучшению. При возврате в работу прежний вывод сохраняется в аудите, а наблюдения после прежнего внедрения получают отметку замещения. Текст публикации редактируется отдельно. Любая правка согласованного материала отменяет согласование.

Незакреплённые загрузки старше 48 часов очищаются worker пакетами до 50 файлов. Сбой удаления оставляет запись для повтора через пять минут. Том файлов должен быть одним и тем же у API и worker. Для копирования приостановите запись обоих процессов и сохраните PostgreSQL и том как одну пару. Файлы доказательств, прикреплённые к улучшению, входят в этот же том.

Репетиция на синтетических данных прошла с PostgreSQL 17 и отдельным файловым каталогом. После `pg_restore` сотрудник открыл исходное обращение и скачал совпадающее по содержимому вложение. Worker обработал контрольное задание на восстановленной БД.

## Квоты и проверка вложений

Применяются суммарная квота 1 ГиБ на загрузившего пользователя и отдельная квота 50 МиБ на незакреплённые файлы. Значения задаются в байтах через `ATTACHMENT_USER_QUOTA_BYTES` и `ATTACHMENT_PENDING_QUOTA_BYTES`. В production ClamD обязателен, также его можно включить для тестового стенда через `ATTACHMENT_SCAN_MODE=required`. Заражённый файл, недоступный сканер или ошибка записи не позволяют сделать вложение доступным. Ранее загруженные файлы без отметки проверки в обязательном режиме скрыты. Подключение задаётся через `CLAMD_SOCKET` в локальной среде или `CLAMD_HOST` и `CLAMD_PORT` в закрытой сети. В «Мониторинге» видны последняя успешная проверка и последние ошибки сканера/хранилища. [Протокол ClamD](https://docs.clamav.net/manual/Usage/ClamdProtocol.html)

## Нагрузочная проверка

Примените миграции и демосид к отдельной базе с именем `modus_*load`. Укажите её в `TEST_DATABASE_URL` и запустите `pnpm -C backend test:load`. Проверка добавляет синтетические обращения, посылает 60 параллельно распределённых запросов очереди и радара и проверяет доставку 120 просроченных сигналов. `LOAD_APPEALS` задаёт объём, `LOAD_P95_MS` — порог измерения. Порог теста не определяет корпоративный SLO.

## Настройка новых каналов

- Для анонимных обращений создайте ключ командой `node -e "console.log(require('node:crypto').randomBytes(32).toString('hex'))"` и передайте его в ANONYMOUS_DATA_KEY для API и worker. Храните ключ отдельно от БД и резервируйте вместе с конфигурацией секретов. Старые диалоги требуют ключа, которым были зашифрованы. Назначьте резервную спецочередь SPECIAL с активным координатором и правом SENSITIVE_CASE_HANDLER. В демонстрационной среде используется демонстрационная очередь.
- Для публичного анонимного канала исключите его страницы и API из журналов доступа, трассировки тел, заголовков и мониторинга запросов на всех внешних прокси. Встроенный Nginx отключает журнал доступа для этих маршрутов и убирает Cookie перед проксированием анонимного API. API использует краткоживущий HMAC сетевого адреса для ограничения запросов. Для индивидуальных лимитов укажите в TRUST_PROXY_HOPS число доверенных прокси перед API. Внешний HTTPS-прокси должен заменить присланный клиентом X-Forwarded-For фактическим адресом клиента. Контейнер API не должен быть доступен в обход цепочки.
- Для ИИ включите GROQ_AI_ENABLED и настройте GROQ_API_KEY. Действующие настройки модели и режим структурированного вывода описаны в [GROQ_AI.md](GROQ_AI.md). Служебные, чувствительные и анонимные данные не передаются при анализе карточек.
- Для демонстрации 1С задайте ONEC_MODE=simulator и DEMO_MODE=true. Симулятор использует отдельный каталог и остатки, изменяемые при создании заявок. Для рабочего обмена задайте ONEC_MODE=http, ONEC_API_URL, ONEC_API_TOKEN и выдайте ONEC_OPERATOR сотрудникам обработки. В production необходим HTTPS. Контракт HTTP-сервиса указан в [API.md](API.md).
- После миграции обновите права роли приложения на новые таблицы через `deploy/runtime-grants.sql`, если production использует отдельную роль PostgreSQL.

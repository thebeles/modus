# Эксплуатация

`docker compose ps -a` показывает состояние процессов. Контейнер migrate после успеха завершается с кодом 0. Проверка /api/v1/health/live проверяет процесс, /api/v1/health/ready проверяет соединение с PostgreSQL. Если API недоступен, начните с `docker compose logs migrate api worker`.

Worker опрашивает очередь каждые две секунды. Уведомления создаются с уникальным ключом. Повторная обработка безопасна. Ошибки доставки повторяются с экспоненциальной задержкой. После шести попыток задача отображается в «Мониторинге». Перезапуск продолжает обработку открытых заданий. Настройте мониторинг числа ожидающих и исчерпанных заданий для промышленной эксплуатации.

## Производственный запуск

Используйте отдельные настройки PostgreSQL и хранилища с резервным копированием. Установите `NODE_ENV=production`, `DEMO_MODE=false`, `SEED_DEMO_USERS=false`, `COOKIE_SECURE=true` и `WEB_ORIGIN` с HTTPS. Перед запуском примените `pnpm db:migrate`. Подайте первый адрес и пароль через менеджер секретов в переменные `BOOTSTRAP_ADMIN_EMAIL` и `BOOTSTRAP_ADMIN_PASSWORD`, выполните `pnpm db:admin`, затем удалите переменные из среды выполнения. Добавьте обычную резервную очередь и резервные очереди специальных классов с действующими координаторами.

## Резервная копия

Согласуйте окно записи, сохраните согласованные снимки базы и тома файлов. Для PostgreSQL используйте `pg_dump -Fc -f kontur.dump` с настроенными `PGHOST`, `PGDATABASE`, `PGUSER` и безопасным источником пароля. Копии храните в зашифрованном хранилище с отдельным доступом. Для проверки восстановите дамп командой `pg_restore --exit-on-error -d <отдельная-база> kontur.dump`, подключите копию тома и проверьте карточку, вложение и обработку outbox. Используйте отдельные секреты и закрытый тестовый адрес для восстановления.

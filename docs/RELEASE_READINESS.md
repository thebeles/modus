# Готовность конкурсного релиза «Модус · Контур»

Ветка `codex/hackathon-release`, проверяемый коммит приложения `0cc28b79290c277f3bb93dfea3b2c6c810a2d039`. Документы приёмки оформлены отдельным коммитом поверх него. В исходном локальном состоянии `main`, `origin/main`, `codex/remediation` и `codex/ux-review` указывали на `50cfbd9488f32c982c04a591e74d077b98febebc`. UX-изменения находились в рабочем дереве. В релиз включены оба набора. `main` и удалённая ветка не менялись.

## Безопасность и восстановление

- `pnpm audit --prod` в backend и frontend вернул `No known vulnerabilities found`. В lockfile `deepmerge-ts@8.0.0`. Аудит контейнерных базовых образов и полный независимый security review не выполнялись.
- В релизном дереве поиск характерных форматов Groq/GitHub-токенов и приватных ключей совпадений не дал. В Git входят шаблоны `.env`, реальные локальные `.env`, хранилище и результаты Playwright исключены. Данные seed синтетические.
- На изолированном API в production-режиме и под отдельной PostgreSQL-ролью `/health/ready` вернул 200, Swagger 404, демовход 403. Обычная тестовая учётная запись получила cookie с `Secure`, `HttpOnly` и `SameSite=Strict`. Разрешённый TXT при недоступном сканере получил 503. TLS на реальном внешнем прокси и живой ClamD остаются открытыми.
- `has_table_privilege` для runtime-роли подтвердил `INSERT=true`, `UPDATE=false`, `DELETE=false`, `TRUNCATE=false` на аудите и `UPDATE=false` на `_prisma_migrations`. Доменная и интеграционная регрессия проверяют пользовательский scope, CSRF, refresh, logout, аудит, квоты и скрытие внутренних данных.
- Браузер создал обращение с TXT. `pg_dump -Fc` и `pg_restore --exit-on-error` перенесли обращение, связанную запись о вложении и событие аудита в другую базу. Файловый архив восстановлен в отдельный том. API с восстановленной БД и томом отдал файл с исходным SHA-256 `a0573450b2452a62235c4ffb91a4170d9127d8887f309de33148db5753e3a14a`. После перезапуска API и worker исходное обращение и файл доступны, heartbeat свежий. Нормативы RPO/RTO и восстановление в корпоративной среде открыты.

### Нагрузка

На каждом прогоне `pnpm -C backend test:load` использовались свежая локальная PostgreSQL, 2 000 синтетических обращений, 6 параллельных клиентов, 60 измеряемых GET-запросов с текстовым фильтром и одновременная доставка 120 уведомлений. Порог P95 команды оставался 1 500 мс.

| Прогон | P95 очереди, мс | P95 Радара, мс | Результат |
|---|---:|---:|---|
| Исходные замеры | 124 / 206 | 1 613 / 1 691 | Порог Радара превышен |
| После объединения агрегатов, параллельно с браузерной приёмкой | 129 | 1 559 | Порог Радара превышен |
| Финальный отдельный прогон | 105 | 898 | Порог пройден, все 120 уведомлений доставлены за 7 593 мс |

Интеграция сверяет агрегаты Радара с отдельными аналитическими API. Значения получены на одном компьютере. Разница между параллельным и отдельным прогонами ограничивает перенос результатов на другие среды. P95 записи обращения и детальных карточек отдельно не измерялся, их функциональность проверена в браузере.
